## 30 秒开场

> 计算机网络我按五层来把握：物理层传比特，链路层负责相邻节点交付，网络层 IP 做尽力而为的转发，传输层 TCP 把不可靠通道变成可靠字节流，应用层是 HTTP、DNS 这些。面试最常问的是 TCP 怎么保证可靠，以及三次握手。

## ★1. TCP 如何保证可靠传输（湖大真题，必须 60 秒）

口述骨架，按这个顺序说，不要漏：

1. **连接管理**：三次握手建立、四次挥手释放，双方确认序号空间。
2. **序号 + 确认**：每个字节有序号；接收方回 ACK，表示期望的下一个字节。
3. **超时重传**：发出去没按时收到 ACK，就重发。超时用 RTT 估计（RTO）。
4. **快速重传**：连续 3 个重复 ACK，不等超时，立刻重发可能丢的那段。
5. **校验和**：段头+数据做校验，出错丢弃等重传。
6. **流量控制**：接收窗口（rwnd）告诉对方还能收多少，防止把接收缓存冲爆。
7. **拥塞控制**：发送窗口还受拥塞窗口 cwnd 限制，按网络状况加减窗。

收口一句：

> TCP 的可靠，不是「绝对不丢」，而是用确认、重传、校验和窗口，把不可靠的 IP 数据报做成对应用看起来可靠的字节流。

### 追问：可靠传输和拥塞控制是一回事吗？

不是。可靠传输解决「丢了补上、顺序对、不出错」；拥塞控制解决「别把网络塞死」。滑动窗口同时受 `min(rwnd, cwnd)` 限制。

## ★2. 为什么要三次握手，两次行不行？

两次不行。

- 第一次 SYN：客户端说「我想连，我的初始序号是 x」。
- 第二次 SYN+ACK：服务器说「收到了，我的初始序号是 y，期望下一个是 x+1」。
- 第三次 ACK：客户端确认「我也能收你的 y」。

两次只能确认**一条方向**的发送能力。第三次是为了：

1. 让服务器确认客户端的接收/发送都正常；
2. **防止已失效的旧 SYN** 突然到达：如果两次握手就建连，迟到的旧 SYN 会让服务器空开一个连接，浪费资源。

### 追问：第三次握手可以带数据吗？

可以。第三次 ACK 可以携带应用数据（TFO 等机制也利用这一点）。前两次通常不带应用数据。

### 追问：握手失败 / SYN 泛洪怎么办？

攻击者狂发 SYN 不回第三次 ACK，服务器半连接队列被占满。防护：SYN Cookie、加大 backlog、限制半连接数。

## ★3. 四次挥手，为什么不是三次？TIME_WAIT 是什么？

TCP 是**全双工**，每边单独关发送方向（半关闭）。

1. 主动方 FIN
2. 被动方 ACK（我还可能有数据要发，所以不能马上 FIN）
3. 被动方数据发完再 FIN
4. 主动方 ACK

若被动方没有剩余数据，第 2、3 步可以合并成一次 FIN+ACK，看起来像三次，但协议允许四次。

**TIME_WAIT（主动关闭方，持续 2MSL）**：

- 保证最后一次 ACK 能到达；丢了对方会重发 FIN，还能再回 ACK。
- 让旧连接的延迟报文在网络中死掉，避免被新连接当成合法数据。

不要说「TIME_WAIT 没用、应该立刻关掉」。高并发下端口被占是工程问题，用 `SO_REUSEADDR` 等处理，不是否定 2MSL。

## 4. 拥塞控制四个阶段

| 阶段 | 触发 | 行为 |
| --- | --- | --- |
| 慢启动 | 连接开始，或超时后 | cwnd 从 1（或更小）指数增长：每个 RTT 翻倍 |
| 拥塞避免 | cwnd 达到 ssthresh | 每个 RTT 大约加 1，线性增长 |
| 快速重传 | 3 个重复 ACK | 立刻重传丢失段，不等超时 |
| 快速恢复 | 快速重传之后（Reno） | ssthresh = cwnd/2，cwnd 降到 ssthresh 附近再线性加，**不退回慢启动** |

超时（RTO）比 3 个重复 ACK 更严重：认为网络很堵，ssthresh 减半，cwnd 回到很小，重新慢启动。

口述别把 Tahoe / Reno / CUBIC 混在一起。本科口径：先讲 Reno 四阶段；被问 Linux 默认，可以说现在常见是 CUBIC / BBR，细节如果没做过就不要编。

## 5. TCP 和 UDP 对比

| | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接 | 无连接 |
| 可靠 | 可靠字节流 | 尽力而为 |
| 顺序 | 保证 | 不保证 |
| 拥塞/流量控制 | 有 | 无 |
| 头部 | 20 字节起 | 8 字节 |
| 场景 | HTTP、文件、SSH | DNS、视频、游戏、QUIC 的底座 |

DNS 用 UDP 是因为查询短、一次一问、丢了应用自己重试，不想付握手代价。HTTP/3 跑在 QUIC（UDP）上，可靠性和握手由 QUIC 自己做。

## 6. HTTP / HTTPS / HTTP 版本

- HTTP 默认 80，明文；HTTPS 默认 443，在 TCP 上套 TLS。
- HTTPS 多了证书认证、密钥协商、对称加密传数据。性能开销主要在握手，会话复用后好很多。
- HTTP/1.1：持久连接、管道（实际很少用）、头部冗余。
- HTTP/2：二进制分帧、多路复用、头部压缩（HPACK），仍是 TCP。队头阻塞在 TCP 层仍在。
- HTTP/3：QUIC over UDP，解决 TCP 队头阻塞，握手更快。

### 追问：从输入 URL 到页面显示发生了什么？

DNS 解析 → 建立 TCP（HTTPS 再 TLS）→ 发 HTTP 请求 → 服务器响应 → 浏览器解析 HTML、拉 CSS/JS/图片（可能再次请求）→ 渲染。能说到「先 DNS 再 TCP 再 TLS」就够。

## 7. DNS、IP、ARP 各干什么

- **DNS**：域名 → IP。递归查询 vs 迭代查询。记录类型 A/AAAA/CNAME/MX。
- **IP**：主机到主机、尽力而为、无连接。IPv4 地址+子网掩码决定网络号。路由器按目的网段转发。
- **ARP**：同一局域网里，IP → MAC。发广播问「谁是这个 IP」，对端回 MAC。

不要把 ARP 说成「跨网段也能 ARP」。跨网段要先交给默认网关，ARP 的是网关的 MAC。

## 8. 五层架构

本科课一般讲这五层，面试按这个说就行：

| 层 | 干什么 | 例子 |
| --- | --- | --- |
| 应用层 | 给用户程序提供服务 | HTTP、DNS、SMTP |
| 传输层 | 进程到进程；可靠或尽力而为 | TCP、UDP |
| 网络层 | 主机到主机、跨网转发 | IP、ICMP、OSPF |
| 数据链路层 | 相邻节点成帧、差错检测 | 以太网、Wi-Fi、ARP |
| 物理层 | 比特怎么在介质上传 | 网线、光纤、调制 |

和另外两套模型的对应：OSI 七层把应用层拆成应用 / 表示 / 会话，TCP/IP 四层把链路+物理合成网络接口层。表示层、会话层在真实协议栈里往往融进应用层。被问「七层还是四层」时说：课上按五层，OSI 是教学模型，实际协议按 TCP/IP 跑。

## 9. 滑动窗口、粘包、队头阻塞

- **滑动窗口**：发送方已发送未确认的数据不能超过窗口。窗口滑动 = 对方 ACK 前进。
- **TCP 粘包**：TCP 是字节流，没有消息边界。应用自己定长度或分隔符。UDP 是数据报，一次 recv 对应一次 send（在 MTU 内）。
- **队头阻塞**：HTTP/1.1 同一连接请求排队；HTTP/2 多路复用缓解应用层阻塞，但 TCP 丢包仍会卡住后面的流；HTTP/3 用 QUIC 多流才从传输层拆开。

---

## 10. 对称加密 vs 非对称加密（常跟 HTTPS 一起问）

- 对称（AES）：快，加密解密同一把钥匙，密钥分发难。
- 非对称（RSA、椭圆曲线）：公钥加密/验签，私钥解密/签名；慢。
- TLS：用非对称（或 DH）协商出会话密钥，后续大数据用对称加密。证书证明公钥属于该网站。
